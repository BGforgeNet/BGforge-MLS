# Supply chain

What a release produces so consumers can verify it, what scans the repository, and the two hardening choices
that are deliberately NOT wired. Read this before a release (it is a step in [releasing.md](releasing.md))
and before adding any security tooling - two of the sections below exist to stop a well-meant addition.

## Provenance artifacts

Release builds produce a CycloneDX SBOM (`dist/sbom.cdx.json`) attached to the GitHub Release, and SLSA
Level 3 provenance generated by `slsa-framework/slsa-github-generator`. Consumers can use these to verify
that a VSIX or npm tarball was produced by the published CI pipeline without tampering.

## Static analysis

OpenSSF Scorecard (`.github/workflows/scorecard.yml`) covers project-process hygiene, and CodeQL
(`.github/workflows/codeql.yml`) runs JavaScript/TypeScript SAST queries. Findings publish to the
repository's GitHub code-scanning surface. The `pnpm supply-chain:verify` script (run as the first CI step)
confirms all four workflow artifacts are present before install.

## Secret scanning is the platform's job

Secret scanning is left to GitHub's native secret scanning and push protection, which apply automatically to
this public repository - a scheduled self-hosted scanner (gitleaks or similar) is intentionally NOT wired and
should not be added. On a public repo it duplicates the platform's coverage while adding a false-positive
allowlist to maintain: the TextMate highlight generators (`scripts/utils/src/update-*-highlight.ts`) emit
high-entropy grammar repository keys (e.g. `weidu-tp2-optexact`) that trip generic-api-key entropy rules. The
secret surface is minimal - there are no runtime credentials, and the only publishing secret (`NPM_TOKEN`) is
a GitHub Actions secret that is never committed - and a full commit-history scan has been run and came back
clean. If a leak is ever suspected, run a scanner on-demand locally (`gitleaks git`) rather than standing up a
workflow; confirm push protection is enabled under repo Settings -> Code security.

## Dependabot version updates are off, security updates are on

Dependabot version-update PRs are intentionally disabled - there is no `.github/dependabot.yml`, and one
should not be added back. Dependency bumps are performed manually as coordinated changes so the LSP
`vscode-languageclient` / `vscode-languageserver` / `vscode-languageserver-protocol` triplet (see
[dependencies.md](dependencies.md)), major-version updates, and any required `pnpm.overrides` adjustments stay
grouped with their rationale rather than landing as separate noisy PRs.

Dependabot _security_ updates are a separate channel toggled in repo Settings -> Code security and remain
enabled; the absence of `dependabot.yml` does not affect them. If a security advisory needs by-name
suppression (e.g., the prior `uuid` case where the vulnerable code path was unreachable), close the PR with a
rationale rather than re-introducing `dependabot.yml` solely to host an `ignore:` entry.
